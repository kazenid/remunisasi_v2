# Implementation Plan — Fix Upload Bukti Tugas v2

Konteks: Laravel 13 + Inertia 3 + Vue 3 (PrimeVue Aura/Sakai + Tailwind v4). UI bahasa Indonesia. Kerja langsung di mainline (tanpa worktree). Ini perbaikan dua bug yang terfokus, bukan fitur baru. Blast radius kecil.

Perintah build & test proyek:
- Backend: `php artisan test` (PHPUnit ^12). Fokus modul: `php artisan test --filter=KatimkerTaskTest` dan `php artisan test --filter=KatimkerSubmitTest`.
- Frontend: `npm run build` (Vite 8). Komponen PrimeVue auto-registered via `unplugin-vue-components` + `@primevue/auto-import-resolver` — jangan import manual.
- Format PHP opsional: `vendor/bin/pint <file>`.

## Temuan investigasi (grounded in code)

- **Nilai batas ukuran selfie = 5120 KB = 5 MB** — `app/Http/Requests/TaskDraftRequest.php` `rules()`: `'foto_selfie.*' => ['file','image','mimes:jpeg,jpg,png','max:5120']`. Field `bukti.*` dan `dokumen.*` = `max:10240` (10 MB). Angka ini harus direfleksikan di pesan error dan di cek sisi klien.
- **Bug 1 akar masalah**: pesan "The foto_selfie.0 failed to upload." adalah pesan BAWAAN Laravel untuk rule `uploaded` (tidak ada folder `lang/` kustom; proyek pakai pesan default bahasa Inggris). Rule `uploaded` gagal ketika PHP menolak file di level ini (`UPLOAD_ERR_INI_SIZE`: file > `upload_max_filesize` tetapi POST masih ter-parse). Pada kasus ini rule `max:` TIDAK ikut jalan, sehingga pesan `foto_selfie.*.max` yang sudah ada tidak pernah tampil. Saat ini `messages()` di `TaskDraftRequest` TIDAK punya entri `*.uploaded`, jadi yang muncul pesan generik.
- **Kasus `post_max_size` terlampaui**: bila total body POST > `post_max_size`, `$_POST`/`$_FILES` kosong dan Laravel melempar `Illuminate\Http\Exceptions\PostTooLargeException` (HTTP 413) — ditangani handler default (bukan validasi), tidak ada pesan Indonesia. `bootstrap/app.php` saat ini hanya mengatur `shouldRenderJsonWhen` untuk `api/*`; tidak ada handler khusus untuk `PostTooLargeException`.
- **Tidak ada cek ukuran sisi klien untuk selfie**: `resources/js/Components/form/SelfieCapture.vue` memakai `<input type="file" accept="image/jpeg,image/png" multiple>` biasa dan langsung `emit('captured', f)` tanpa validasi ukuran. Field `bukti` memakai PrimeVue `FileUpload` dengan `:maxFileSize="10485760"` TAPI event penolakan ukuran tidak ditangani/di-toast (lihat `TaskForm.vue` `onBukti` hanya membaca `event.files`). Jadi oversize di sisi klien tidak memunculkan pesan jelas.
- **Bug 2 akar masalah (double toast)**: pada `resources/js/Pages/Katimker/TaskList.vue` `konfirmasiAjukan()` memanggil `router.post(route('katimker.tugas.submit', ...))` dengan `onSuccess` yang menampilkan toast "Diajukan". Backend `TaskController@submit` menangani kegagalan (mis. tanpa selfie) dengan `return back()->with('error', $e->getMessage())` — ini **redirect 302 → 200** yang oleh Inertia dianggap SUKSES (bukan validation error / 422). Akibatnya `onSuccess` MENYALA (toast sukses) BERSAMAAN dengan `watch(() => page.props.flash?.error, ...)` yang menyalakan toast error → dua notifikasi. Dikonfirmasi lewat `KatimkerSubmitTest::test_submit_tanpa_selfie_ditolak` yang meng-assert `assertRedirect(...)->assertSessionHas('error')`.
- **Risiko serupa di `TaskForm.vue`**: `submit()` punya `onSuccess` (toast "Draf tersimpan.") dan juga `watch(() => page.props.flash?.error, ..., { immediate: true })`. Jika `store`/`update` menangkap `\RuntimeException` lalu `back()->withErrors(...)->with('error', ...)`, Inertia melihat validation errors (via `withErrors`) sehingga `onError` yang jalan, bukan `onSuccess` — jadi di jalur ini tidak dobel. Namun `watch` dengan `immediate: true` berisiko menampilkan flash error "basi" dari kunjungan sebelumnya saat halaman form pertama kali dimuat. Perbaiki agar konsisten: flash hanya ditampilkan saat benar-benar berubah dan bukan null.

## Keputusan desain (ringkas, dengan alasan)

1. **Bug 2 — hentikan toast sukses pada submit yang gagal.** Perbaikan utama di frontend `TaskList.vue`: pindahkan penampilan toast sukses submit ke pengecekan flash `success` server, atau cegah `onSuccess` menyala saat ada flash `error`. Alasan paling tahan-regresi dan paling sesuai pola proyek: **jadikan toast sukses submit didorong oleh flash `success` server** (bukan oleh callback `onSuccess` Inertia), karena server adalah sumber kebenaran apakah pengajuan benar-benar berhasil (`redirect()->...->with('success', 'Tugas berhasil diajukan.')`) atau gagal (`back()->with('error', ...)`). Dengan begitu: submit gagal → hanya flash `error` → satu toast error; submit sukses → hanya flash `success` → satu toast sukses. Hapus `onSuccess` toast di `konfirmasiAjukan`. (Alternatif ditolak: mengubah backend agar submit yang gagal mengembalikan 422/`withErrors` — itu mengubah kontrak `KatimkerSubmitTest` yang meng-assert `assertSessionHas('error')` + `assertRedirect`, blast radius lebih besar.)
2. **Flash watcher jadi aman & anti-duplikat.** Satukan pola watch flash: watch `success` DAN `error`, tanpa `immediate: true` untuk `success` (agar tidak memunculkan toast sukses basi), dan untuk `error` tetap aman karena backend hanya mengisi `error` saat benar-benar gagal. Alasan: flash Laravel adalah one-time (`session()->get()` di `HandleInertiaRequests`), namun prop tetap ada pada response saat ini; `immediate:true` bisa menembakkan toast untuk nilai yang sudah "dikonsumsi" secara visual pada navigasi berikutnya. Tangani dengan hanya bereaksi pada perubahan nilai non-null.
3. **Bug 1 — pesan jelas untuk oversize, tiga lapis.**
   - (a) **Pesan validasi kustom backend** di `TaskDraftRequest::messages()` untuk rule `uploaded` dan `max` pada `foto_selfie.*` dan `bukti.*`, menyebut batas MB. Rule `uploaded` adalah rule implisit yang jalan untuk setiap `file`; menambah pesan `foto_selfie.*.uploaded` menggantikan "failed to upload" generik untuk kasus `UPLOAD_ERR_INI_SIZE` (file > `upload_max_filesize` tetapi POST ter-parse). Alasan: ini backstop server yang menutup kasus (b) deskripsi tugas.
   - (b) **Handler `PostTooLargeException`** di `bootstrap/app.php` → kembalikan `back()->with('error', 'Ukuran total unggahan melebihi batas server. Perkecil atau kurangi jumlah berkas (maks 5 MB per foto selfie, 10 MB per dokumen).')` untuk request web (non-api). Alasan: menutup kasus `post_max_size` terlampaui yang tidak lewat jalur validasi; tetap konsisten dengan mekanisme flash `error` yang sudah ada → otomatis jadi satu toast error (lihat Keputusan 2).
   - (c) **Cek ukuran sisi klien sebagai penjaga utama**: tolak file oversize sebelum submit dengan toast jelas, dan jangan kirim. Untuk selfie (input biasa di `SelfieCapture.vue`) tambahkan cek 5 MB; untuk `bukti` (PrimeVue FileUpload) tangani penolakan `maxFileSize` dan tampilkan toast. Alasan: deskripsi tugas meminta cek klien sebagai penjaga utama.
4. **Konstanta ukuran tunggal di frontend.** Definisikan `MAKS_SELFIE_MB = 5` dan `MAKS_BUKTI_MB = 10` di `TaskForm.vue` (dan teruskan batas selfie ke `SelfieCapture.vue` via prop `:maxSizeMb="5"`) agar angka cocok dengan `max:5120`/`max:10240` backend. Alasan: satu sumber angka, hindari drift.

## Catatan & asumsi

- **Nilai batas dikonfirmasi dari kode**: selfie 5 MB (`max:5120`), bukti/dokumen 10 MB (`max:10240`). Semua pesan dan cek klien memakai angka ini.
- **Bug 1 jalur `post_max_size`**: reproduksi riil bergantung `php.ini` lingkungan (tidak ada override di repo). Handler `PostTooLargeException` (langkah 2) adalah penutup backend; verifikasi penuh butuh uji manual dengan `post_max_size` kecil — ditandai needs-verification-during-implementation, TIDAK diabaikan.
- **Bug 2 jalur sukses-palsu**: dikonfirmasi dari kontrak `KatimkerSubmitTest` (`back()->with('error')` + `assertRedirect`) yang membuat Inertia menganggap submit gagal sebagai "sukses" di callback. Perbaikan dilakukan di frontend (menggerakkan toast dari flash server) agar kontrak backend/test tetap utuh (blast radius kecil).
- **Flash one-time**: `HandleInertiaRequests::share()` memakai `session()->get(...)` untuk `success`/`error`/`warning`/`info`; nilai hanya ada pada response saat redirect. Menghindari `immediate: true` pada watcher mencegah toast basi.
- **Tidak mengubah**: rules validasi lain, enum `tipe`, skema DB, policy, route, alur draft/submit/review, dan field `bukti`/`dokumen` yang sudah ada. Happy path (file ukuran valid) tetap sukses dengan tepat satu toast sukses.
- Jika `send_message`/tooling tidak tersedia, plan ini tetap menjadi acuan loop implementasi berikutnya.
